# 넉넉 백엔드 개발 규칙

## 서비스 개요

넉넉은 카드 이용자의 가용잔고를 산출하고, 보유 카드 중 어떤 카드로 언제 결제할지를 계산해 제시하는 서비스다. 백엔드는 세 영역으로 나뉜다.

- 데이터 계층: 마이데이터 규격 목 어댑터, RAG 기반 약관 규칙 변환
- 연산 계층: 결제 조합 최적화 엔진, 변동 지출 시계열 예측
- API 계층: REST 엔드포인트, LLM 호출 오케스트레이션

## 절대 규칙

### 금액 계산에 LLM을 쓰지 않는다

실적 충족 여부, 할인액, 잔고 산출은 반드시 규칙 엔진이 계산한다. LLM은 다음 세 가지만 담당한다.

- 약관 텍스트를 조건식으로 변환 (배치 처리, 사람 검수 후 반영)
- 사용자 질의에서 파라미터 추출
- 이미 계산된 결과를 자연어로 설명

LLM에게 숫자를 계산하게 하거나, 계산 결과를 검증 없이 사용하는 코드를 작성하지 않는다.

### 스키마와 응답 형식은 임의로 바꾸지 않는다

`references/schema.sql`과 `references/api-spec.yaml`에 정의된 테이블 구조와 응답 형식을 그대로 사용한다. 필드명을 바꾸거나 새 필드를 추가해야 한다면 코드를 작성하는 대신 그 사실을 먼저 알린다.

### 마이데이터 접근은 인터페이스를 통한다

거래 데이터 조회는 반드시 추상화된 인터페이스를 거친다. 구현체는 목업, 파일 업로드, 실연동 세 가지이며 상위 로직은 어떤 구현체인지 알지 못해야 한다.

## 코드 작성 기준

### 계층 분리

컨트롤러는 요청 검증과 응답 변환만 한다. 비즈니스 로직은 서비스 계층에, 데이터 접근은 리포지토리 계층에 둔다. 컨트롤러에서 직접 쿼리를 실행하지 않는다.

### 예외 처리

외부 호출(LLM API, 파일 파싱)에는 반드시 타임아웃과 예외 처리를 넣는다. 시연 중 오류가 나면 화면이 멈추므로, 실패 시 대체 응답을 반환하는 경로를 함께 만든다.

### 로깅

외부 API 호출, 최적화 연산 시작과 종료, 예외 발생 지점에 로그를 남긴다. 개인 금융정보는 로그에 남기지 않는다.

### 주석

핵심 로직에는 무엇을 하는지가 아니라 왜 그렇게 했는지를 주석으로 남긴다. 특히 최적화 엔진의 가지치기 조건, 예측 모듈의 보정 계수는 근거를 적는다.

### 하드코딩 금지

카드 규칙, 임계값, 외부 URL은 설정 파일이나 데이터베이스에서 읽는다. 시연용 임시값을 넣었다면 주석에 `TODO`로 표시한다.

## 최적화 엔진 작성 시

조합 탐색은 다음 순서로 구성한다.

1. 실적 충족이 불가능하거나 잔고 하한을 위반하는 조합을 탐색 전에 제외
2. 월별 확정 지출 스케줄은 조합과 무관하므로 한 번만 계산해 재사용
3. 현재 최선해보다 이론상 최대 혜택이 낮은 분기는 탐색 중단
4. 카드 규칙은 변경 빈도가 낮으므로 메모리에 캐싱

성능 개선 코드를 작성할 때는 개선 전후를 비교할 수 있도록 측정 지점을 함께 넣는다.

## 예측 모듈 작성 시

- 확정 지출과 변동 지출을 분리한다. 확정 지출은 계산, 변동 지출만 예측 대상이다.
- 점 추정은 카테고리별로 나눠 계산한다. 전체를 한 번에 예측하지 않는다.
- **분위수 밴드는 카테고리별로 구해 합산하지 않는다.** 카테고리마다 q25/q75를 뽑아
  더하면 모든 카테고리가 같은 달에 동시에 고점을 찍는다고 가정하는 것과 같아 밴드가
  2~3배로 부풀려진다(시연 데이터 실측: 총액 기준 0.13~0.18 → 합산 기준 0.26~0.53).
  카테고리별 점 추정을 합산해 기준값을 만들고, **총액 표본**에서 구한 비율을 곱한다.
  근거는 `docs/decisions/005` 참조.
- 이동평균과 중앙값을 함께 사용한다. 중앙값은 일회성 대형 지출의 왜곡을 막는 용도다.
- 단일 예측값을 반환하지 않는다. 25/50/75 분위수 기반 세 가지 시나리오를 반환한다.
- 완결되지 않은 달(오늘이 속한 달)은 표본에서 뺀다. 지출이 준 것이 아니라 달이 덜
  지난 것인데, 그대로 넣으면 모든 예측이 아래로 끌린다.
- 딥러닝 모델을 제안하지 않는다. 개인 단위 데이터는 표본이 적어 과적합된다.

## 커밋

Conventional Commits 형식을 따른다.

```
feat: 결제 조합 최적화 엔진 가지치기 로직 추가
fix: 전월실적 산정 시 무이자 할부 제외 누락 수정
refactor: 거래 데이터 조회를 인터페이스로 분리
test: 실적 판정 로직 단위 테스트 추가
```

브랜치는 `feat/`, `fix/`, `refactor/` 접두사를 사용한다.

## 보안

- API 키와 데이터베이스 접속 정보는 환경변수로 관리하고 코드에 직접 쓰지 않는다.
- 사용자 업로드 파일은 확장자와 크기를 검증한다.
- 외부 URL을 받아 요청하는 코드는 작성하지 않는다.
- 개인 금융정보는 필요 범위를 넘어 저장하지 않는다.
