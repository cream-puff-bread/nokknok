## 결정 1. LLM 제공자 — 확정: Gemini

### 배경

`.env.example` 에 `LLM_API_KEY` 와 `LLM_MODEL` 이 있고 `httpx` 와 `tenacity` 도 준비되어
있었으나, 제공자를 확정하지 않아 `requirements.txt` 의 SDK가 주석 처리된 상태였다.

임베딩을 쓰지 않기로 했으므로(001) **규칙 변환과 결과 설명에 쓸 모델 하나만** 정하면 된다.

### 고려한 점

| 항목 | 내용 |
|---|---|
| 사용처 | 약관 → 조건식 변환(배치), 질의 파라미터 추출(런타임), 결과 설명 생성(런타임) |
| **구조화된 출력** | **가장 중요한 항목.** 아래 별도 절 참조 |
| 정확성 요구 | 배치는 사람 검수 게이트가 있어 완벽할 필요 없음. 런타임 파라미터 추출은 실패 시 422 응답 |
| 응답 속도 | 런타임 설명 생성은 총 3.5초 예산. 모델 지연이 예산을 넘기면 항상 null이 된다 |
| 비용 | 무료 티어 사용. 약관 변환 결과를 파일로 캐싱해 반복 호출을 막는다 |
| Rate limit | 무료 티어는 분당·일일 요청 한도가 낮다. 배치에서 429가 나기 쉽다 |
| 데이터 취급 | 무료 티어 입출력이 모델 개선에 사용될 수 있다. 아래 별도 절 참조 |

### 구조화된 출력 지원이 결정적이다

이 프로젝트에서 LLM 출력이 가장 실패하기 쉬운 지점은 문장 품질이 아니라
**출력 형식이 계약과 정확히 맞는가**이다.

| 필드 | 요구 조건 |
|---|---|
| `ParsedQuery.category` | `spend_category` 코드와 정확히 일치. 오탈자 시 매칭 실패 |
| `ParsedQuery.paymentType` | `LUMP` / `INSTALLMENT` / `INTEREST_FREE` 중 정확히 하나 |
| 약관 변환 결과 | 기준금액·할인율·제외항목이 규칙 테이블 스키마에 그대로 들어가야 함 |

모델이 자유 텍스트로 답하고 별도 파싱을 거치는 구조면 `/api/simulate` 의
422(파싱 실패) 비율이 눈에 띄게 올라간다.

**Gemini를 선택한 가장 큰 이유가 이것이다.** 응답 스키마를 지정해 JSON 출력을
강제할 수 있고, enum 값 집합도 스키마에 명시할 수 있다. 카테고리와 결제 유형처럼
값이 고정된 필드는 모델이 임의의 문자열을 낼 여지 자체가 없어진다.

응답 스키마는 `spend_category` 테이블과 `contracts/types.ts` 를 단일 원본으로 삼아
생성한다. 코드에 값 목록을 다시 적으면 계약과 어긋난다.

### 데이터 취급 주의

무료 티어는 입출력이 모델 개선에 사용될 수 있다. 본 서비스는 아래 이유로 현 단계에서는
문제가 되지 않는다.

- 이용자 거래 데이터는 전부 자체 생성한 가상 페르소나다
- 약관은 카드사가 공개한 자료다
- 실제 개인 금융정보를 전송하지 않는다

**다만 파일 업로드 경로를 실제로 열게 되면 이야기가 달라진다.** 이용자가 올린 실제
명세서를 무료 티어로 보내면 안 된다. 그 시점에는 유료 전환 또는 업로드 경로에서만
LLM 호출을 제외하는 방식을 검토한다. 시연은 페르소나 경로를 기본으로 하므로
현재 계획에는 영향이 없다.

### 결정 사항

- **제공자 및 모델**: Google Gemini. 무료 티어의 Flash 계열 모델을 사용한다.
  구체적 모델 ID는 회의 시점의 무료 티어 제공 목록을 확인해 확정한다.
  무료 티어 구성은 자주 바뀌므로 공식 문서를 기준으로 삼는다.
- **SDK**: `google-genai` 사용. 응답 스키마 지정을 SDK가 지원하므로 직접 REST를
  호출하는 것보다 이점이 크다.
- **근거**: 무료 티어로 시작할 수 있고, 응답 스키마 기반 구조화된 출력을 지원해
  계약 파일과의 형식 불일치 위험이 낮다.

### 확정 후 확인할 것

- 선택한 모델의 실제 응답 시간이 런타임 예산(3.5초) 안에 들어오는지 측정
- 무료 티어의 분당·일일 요청 한도가 약관 변환 물량을 감당하는지 확인.
  부족하면 배치를 여러 날에 나눠 돌리거나 변환 결과 캐싱을 강화한다
- 429 응답의 `Retry-After` 헤더를 재시도 로직이 실제로 따르는지 확인

## 결정 2. 배치 파이프라인 구조 — 확정: 1단계

### 배경

약관에서 규칙을 뽑고 근거 조항을 연결하는 방식이 두 가지다.

**1단계 구조** — 조항을 순차 처리하며 각 조항에서 그 자리에서 규칙을 추출한다.
추출 시점에 `clause_source.id` 를 이미 알고 있으므로 그대로 함께 저장한다.
조항 검색이 아예 필요 없다.

**2단계 구조** — 조항을 먼저 전부 적재하고, 이후 규칙과 조항을 따로 매칭한다.
매칭 단계에서 검색이 필요하며, `pg_trgm` 유사도를 쓴다.

### 1단계를 택한 근거

**매칭을 위한 재작업이 사라진다.** 2단계는 조항을 먼저 전부 적재한 뒤, 이미 뽑아둔
규칙과 조항을 다시 이어 붙이는 단계를 별도로 거쳐야 한다. 1단계는 규칙을 뽑는 그 순간
`clause_source.id` 를 이미 쥐고 있으므로 이 단계 자체가 없다.

**매칭 정확도를 검증할 필요가 없어진다.** 2단계에서 유사도로 매칭하면 "이 규칙의 근거가
정말 이 조항인가"를 사람이 일일이 확인해야 한다. 1단계는 애초에 그 조항을 읽고 뽑은
규칙이므로 검수 게이트에서는 규칙 자체의 정확성만 보면 된다.

**근거가 어긋날 여지가 구조적으로 없다.** 화면에 표시하는 근거 조항이 실제 계산에 쓰인
조항과 다르면 이 기능은 무의미해진다. 1단계에서는 그런 상황이 발생할 수 없다.

※ LLM 호출 횟수는 두 방식이 같다. 2단계의 매칭은 SQL 유사도 검색이지 LLM 호출이
아니므로, 규칙 추출 호출(섹션당 1회)은 어느 쪽이든 동일하다. 1단계의 이점은 호출량이
아니라 검증 부담과 정확성에 있다.

### 청킹 단위 주의

**토큰 수가 아닌 조항·섹션 단위로 분할한다.** 실제 카드 약관은 혜택 조건이 표에,
제외 항목이 별도 유의사항 절에 있는 경우가 많다. 고정 길이로 자르면 표가 중간에
끊겨 규칙 추출이 실패한다.

스키마가 이를 지원한다. `card_benefit_rule.clause_id` 와 `card_exclusion.clause_id` 가
따로 있으므로, 혜택 표에서 뽑은 규칙과 유의사항에서 뽑은 제외 항목이 각각 다른 조항을
가리켜도 된다.

### 처리 흐름

```
PDF → 섹션 단위 분할
      ↓
   각 섹션마다:
      1. clause_source에 INSERT → id 확보
      2. 같은 섹션 텍스트를 Gemini에 전달 (응답 스키마 지정)
      3. 반환된 규칙·제외 항목에 1의 id를 붙여 INSERT
      4. verified = false 로 저장
      ↓
   사람 검수 → verified = true
```

`clause_source.id` 를 LLM 호출 전에 이미 확보하므로 검색이 낄 자리가 없다.

### 결정 사항

- **파이프라인 구조**: 1단계. 섹션 단위로 조항을 적재하면서 그 자리에서 규칙을
  추출하고 `clause_source.id` 를 함께 저장한다.
- **스키마 정리**: `pg_trgm` 확장과 `idx_clause_content_trgm` 인덱스를 제거했다.
  `clause_source` 는 순수 원문 보관 테이블이 되었다.
- **근거**: 매칭 재작업 제거, 매칭 검증 불필요, 근거 조항 불일치 가능성 원천 차단.
